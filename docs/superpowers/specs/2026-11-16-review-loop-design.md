# taskctl 复核流水线设计（2026-11-16）

状态：待批准
分支：`feat/review-loop`

## 1. 意图与为什么

现在的 taskctl 能安全地跑一个任务：领锁、执行、跑验收命令、证据绑定、fail-closed。但它只覆盖了「执行」这一段。真实工作里，问题出在这段的**两头**：

- 前面：用户给的是目标、背景、边界，是定性的。agent 拿到就开始干，干到一半才发现理解偏了。
- 后面：验收命令只能证明「命令绿了」，证明不了「这事是不是我要的」。缺一个独立判断。

所以目标不是「加一个复核按钮」，而是把一条从意图到可信结果的链路补完整，并且让这条链路**越用越省人**：

```
意图（定性）
  → 澄清：agent 起草 spec（目标/非目标/验收标准/边界/假设），复杂任务等人签字
  → 拆分：找耦合、合并、重切，直到每个单元可独立验收
  → 执行：多任务并跑，各自独占工作目录
  → 复核：独立会话按 spec 的 criteria 判定，不通过就打回
  → 人工：只抽查和核心任务；结果归因到环节，成为改进材料
```

## 2. 目标

1. 复杂任务在动工前产出可判定的 spec，且**由用户确认**；简单任务跳过确认但同样留 spec。
2. 任务可以并行跑，多个任务同时在不同工作目录里执行。
3. 每个「完成」都有独立复核，复核失败自动打回，带具体返工项。
4. 用户只处理：待确认的 spec、耦合清单、复核失败超限的任务、需要人工放行的核心任务、抽查。
5. 每次人工判定都归因到环节（澄清/执行/复核），并汇总成「哪个环节不可靠」。
6. 偏好与判断标准沉淀成一份可读档案，注入下一轮澄清，参与度随确认记录增加而下降。

## 3. 非目标

- 不做看板、Web UI、SQLite；不引入宿主依赖。（总台账是 CLI 文本视图，不是 UI；Web UI 留到 P3 之后。）
- 不做模型训练或微调；「学习」只通过可读档案注入实现。
- 不自动合并、不自动部署、不自动开 PR。
- 不做通用依赖图调度；只支持一层的 `depends_on`。
- 不追求「零人工」；目标是人工只花在判断上，不花在搬运上。

## 4. 反目标

- 加了复核之后人工反而变多。
- 模板膨胀成一张要填二十行的表单。
- 任务状态出现两份可写副本。
- 复核变成「另一个 agent 说好」——没有证据、不可复查。
- 为了自动化把无法判定的东西标成通过。

## 5. 约束

- Markdown 是任务状态的唯一权威；运行记录只拥有事实，不拥有状态（沿用 ADR-0007）。
- 保持 ADR-0007 的 fencing、工作区独占、fail-closed 不变；本设计在它之上加阶段。
- 纯 CLI，无依赖新增（沿用绑定约束）。
- 协作式协议，不是安全边界：worker 与 reviewer 同权限时，自动放行只是流程规则。

## 6. 方案选择

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 以 DSH Taskboard 为底座 | 复用它的 SQLite、UI、claim、automation，在 `in_review` 后加复核 | 任务锁在 DSH 宿主里，与「能在 opencode/Kimi/Pi 里跑、纯 CLI」直接冲突；它的强项（看板/甘特/附件）是本项目的非目标 |
| B. 扩展 taskctl | 在现有 Markdown + fencing + 证据之上补澄清、拆分、复核、归因 | 需要自己做调度与阶段，工作量大；但保住可移植与可版本化 |
| C. 先 Taskboard 试点再迁移 | 用 Taskboard 跑真实任务收集摩擦，再迁回 taskctl | 多一次迁移；但能拿到真实使用数据 |

选 **B**。A 和 C 都会把主战场放到一个绑宿主的数据模型上，而可移植性是本项目存在的理由。Taskboard 仍然保留为参照物：它的 review 状态机、乐观版本、claim 语义值得对照，但不作为运行时依赖。

## 7. 流水线

状态（`tasks/<id>.md` 的 `status`）：

```
draft ──(spec 起草完成，简单任务或已批准)──→ open
open ──(claim)──→ running
running ──(验收命令通过)──→ review
review ──(复核通过且非核心)──→ done
review ──(复核通过且核心/高风险)──→ awaiting-human ──(accept)──→ done
review ──(复核失败)──→ open（返工，写反馈笔记，计一轮）
review ──(无法判定/执行不确定)──→ awaiting-human（人工裁决）
任意 ──(重试耗尽/复核轮次耗尽)──→ blocked
awaiting-human ──(reject)──→ open（带意见）
```

`draft`、`awaiting-human` 是**人工节点**，agent 不写入；`review` 是编排器内部的短阶段。

## 8. 关键设计

### 8.1 八股文模板（intake）

澄清不是空白对话。每个任务先给一份模板，字段分三类，用户只需要填第一类：

| 类别 | 谁来做 | 规则 |
| --- | --- | --- |
| **必答** | 用户给 | 只有用户知道、且猜错代价大的：终态、禁区、算完成的标准、额度/截止 |
| **可推** | agent 推，写出来让用户划 | 从仓库、历史任务、偏好档案、同类任务惯例推；推错由用户否掉 |
| **补问** | agent 问，最多 3 条 | 只问「影响验收」的空白；一次问完，不逐条来回 |

原则：**能推的不要问，问的要能改变结果。** 用户划掉一个「可推」项的成本，远低于回答一个开放问题的成本。

代码类任务的模板（其余三类同构，字段不同）：

```
必答
  1. 做完之后是什么样（一句话，可观察）
  2. 不许动的东西
  3. 怎么算完成（可跑的检查，或可见的现象）
  4. 额度/截止（没有就写"无"）

可推（我写，你划）
  - 要改哪些文件/目录（我读仓库推）
  - 技术路线与依赖
  - 验收命令（从仓库现有脚本推）
  - 既有约定与风格

补问（最多 3 条）
  - 只在影响验收时问，例如"要不要兼容旧数据"
```

其它三类的差异只在字段：办公类是交付物形态、受众、版式与命名约定；调研类是问题边界、来源可信度要求、结论形式；设计类是判据（谁看、看什么、什么算难用）。

模板本身也要瘦：超过屏幕一屏就是失败。

### 8.2 意图与 spec

`taskctl add "<意图原话>"` 把原话落成任务正文（不改写），并触发一次澄清会话。澄清会话产出 `tasks/<id>/spec.md`：

```
## 目标          一两句，可验收的终态
## 非目标        明确不做的事
## 验收标准      C1 / C2 …（每条必须可判定：命令、可观察产物，或可引用的事实）
## 边界          允许改什么、不许动什么、能花多少时间/额度
## 假设          没确认但先按此执行的前提
## 拆分候选      见 8.2
```

验收标准同时以数组写进 frontmatter（`criteria: ["C1 …", "C2 …"]`），让复核结果可以逐条对应。

**虚词消歧**：意图原话必须原样保留，但 spec 里单列一节「模糊表述」，把「差不多」「尽量」「20%」这类词摘出来，给出它的解释和影响面。补问优先问这些，而不是问能从仓库推出来的事。判断标准很简单：能落成命令或可观察现象的，才算消歧完成。

**复杂度判定**：默认 `complex`。只有当用户在意图里明说「简单任务」之类，或在命令上加 `--simple`，才降为 `simple`。规则写进澄清提示词：**没有明说就按复杂处理，不许自行降级**。简单任务的 spec 照样产出，但不停下来等签字，直接 `open`；假设写进 spec，复核时专门核对这些假设有没有被悄悄改掉。

### 8.3 拆分与解耦

独立性由机械判据裁定，不由讨论裁定：**两个单元的写作用域有交集就不独立**。写作用域 = 计划改动的文件/目录/数据集/文档；交集判定用规范化路径比较。

三类耦合，三种处理：

| 耦合 | 处理 |
| --- | --- |
| 共享产物（同一份输出） | 合并成一个任务 |
| 共享决策（B 的验收取决于 A 的选择） | 先出一个「决策任务」，结论落成文件，后续任务引用 |
| 纯顺序（无内容共享，只是先后） | 不合并；保持独立单元，用 `depends_on` 表达先后 |

迭代上限 **两轮**：两轮后仍有交集的，直接合并，不再讨论。

复杂任务的拆分结果以**三行清单**呈现给用户：

```
合并：A+B（共享 docs/x.md）
并行：C、D（写作用域不相交）
等待：E（依赖 C）
```

用户改完，剩下的由 agent 落成子任务文件与 `depends_on`。

### 8.4 执行

- `taskctl run --parallel N`：按工作目录分池，同一个工作目录同时只有一个任务（工作区独占不变）。
- 每个任务自带 `workdir`（frontmatter，相对 `taskctl.json` 的 `workdir`）；父子任务共享背景但各自目录，避免改同一片文件。
- 调度只领取 `open` 且 `depends_on` 全部 `done` 的任务。

### 8.5 复核

复核是**独立会话**：新会话、不传 worker 的 session id、不传 worker 的对话，只给：

- spec（含 criteria 与假设）
- 验收命令、退出码、输出
- 产物摘要在验收前后的值
- 最新交接笔记、`## Files` 清单
- 运行日志尾部

评审输出结构化 JSON：

```json
{
  "verdict": "pass" | "fail" | "unclear",
  "criteria": [{ "id": "C1", "pass": true, "evidence": "test exit 0" }],
  "defects": ["导出按钮仍写死宽度"],
  "summary": "一句话"
}
```

规则：
- 任一 criterion 未过 → `fail`，写反馈笔记，任务回 `open`，计一轮返工。
- 无法判定或复核执行不确定 → `unclear`，转 `awaiting-human`，不自动重试。
- 复核轮次超过 `maxReviewRounds`（默认 2）→ `blocked`，等人工。
- 复核模型可单独指定（`reviewerModel`），默认与执行相同。

### 8.6 人工节点

- `awaiting-human`：核心/高风险任务复核通过后停在这里；复核不确定的也停在这里。
- `accept`：写入 `done`，记审计 `pass`。
- `reject --reason … --stage worker|reviewer|clarify`：写反馈笔记，回 `open`，记审计 `fail`，并标记重点。
- `audit`：对已 `done` 的任务抽查，同样记审计与归因。

归因是这套设计的核心产出：**问题出在澄清（spec 本身就是错的）、执行（没做到 spec）、还是复核（漏判）**。同一个阶段连续失败就是「该改这里」。

### 8.7 日志与报告

- `tasks/<id>/journal.md`：编排器写的追加式单文件日志，一行一条（时间、阶段、事件、详情）。不用 JSONL 分片，便于 diff 和人读。
- `taskctl report <id>`：把 spec、验收证据、复核判定、日志尾部、审计记录拼成一页，供人工抽查时看。
- 交付物本身不复制进任务目录，只记引用（路径 + 摘要），避免出现两份真相。

### 8.8 总台账（`taskctl board`）

用户不需要逐个打开任务，但必须一眼看到「还有什么没做完」。**台账是一份生成出来的 Markdown 文件**：`.taskctl/board.md`，每个任务状态变化后重写，用浏览器/编辑器打开即可自动刷新——展示层由外部工具负责，本项目不做 Web UI。

文件形态（分组 + 计数 + 每行当前卡点）：

```markdown
# taskctl · 2026-11-16 02:50

## 待我确认 2
- 005 登录页改版 · complex · 2h · spec 3/5 条待定
- 007 季度报告初稿 · complex · 1d · 假设 2 条

## 待我放行 1
- ★ 004 支付回调修复 · high · 4h · 复核全绿

## 进行中 3
- 008 CLI 帮助重写 · worker · 12m · turn 3
- 009 文档站调研 · review · 3m · 复核中
- 006 导出按钮 · 返工 第2轮 · 上次：宽度仍写死

## 卡住 1
- 003 数据迁移 · blocked · 复核 2 轮未过：列类型仍不匹配

## 已完成 12（近 7 天）
```

规则：
- 「没做完」= 前四组之和；完成数单独一组，不混进去。
- 每行必须带**当前卡住的原因**（等签字 / 返工原因 / 失败原因），不需要再点进去查。
- 文件是可再生的生成物，不承载状态；手改会被下一次重写覆盖（表头写明）。
- 重写用 `.tmp` + rename，浏览器不会读到半个文件。
- 终端仍打印同一份内容的简表，方便 SSH 下看；`--json` 输出机器可读结构。
- 默认只看未完成；`--all` 才展开已完成。
- 文件放在 `.taskctl/` 而不是 `tasks/`：`TaskStore` 把 `tasks/*.md` 都当任务，放进去会被误读成任务。

### 8.9 学习

- `.taskctl/profile.md`：用户偏好档案（可读、可手改），注入下一次澄清与复核。记录的是「偏好/边界/常见返工项」，不是对话摘要。
- `taskctl metrics`：按阶段统计审计通过率、返工率、复核误判率；连续失误的阶段给建议。
- 更新方式：显式 `taskctl learn`，或在任务收尾时由 agent 提出 diff 由用户确认。**不允许静默改档案**。
- 用户中途打断并说「这样做更好」时，把原话和改法记成一条观察（原话 + 规则），进档案的待确认区；下次同类任务先按新规则走。

## 9. CLI 面

```
taskctl add "<意图>" [--workdir <p>] [--simple] [--risk high] [--type code|office|research|design]
taskctl template <type>                   # 单独看某类模板
taskctl spec <id>                         # 打印 spec.md
taskctl approve <id>                      # 确认 spec → open
taskctl split <id> [--apply]              # 出耦合清单与合并建议；--apply 落成子任务
taskctl run [--parallel N]
taskctl board [--all] [--json]            # 总台账：待确认 / 待放行 / 进行中 / 卡住
taskctl status                            # 一行一任务：阶段、轮次、审查态
taskctl report <id>
taskctl accept <id>
taskctl reject <id> --reason "…" [--stage worker|reviewer|clarify]
taskctl audit <id> --verdict pass|fail [--stage …] [--note "…"]
taskctl metrics
```

## 11. 分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| P1 | spec 阶段（add/spec/approve）、复杂度路由、复核阶段、反馈返工、`board` 总台账、report、accept/reject/audit、并行调度、per-task workdir | 用 opencode 跑通一个复杂任务：出稿 → 签字 → 拆 → 并跑 → 复核失败打回 → 返工通过 → 抽查通过；`board` 能正确显示每个未完成任务的卡点；全程无手工改状态 |
| P2 | DSH / Kimi adapter、耦合清单自动产出、偏好档案注入 | 同一任务换后端能跑；清单确实拦住了一次「共享产物」误拆 |
| P3 | Pi adapter、metrics 归因统计、批次视图 | 连续两周真实使用后，人工分钟数下降可测 |

P1 不做：依赖图、自动合并、多 worker 抢占同一目录、跨机器。

## 12. 已知风险

1. **把握度自欺**：C 模式要求 agent 诚实评估「我不确定什么」。缓解：只对显式标记的简单任务开放；假设必须落文字；复核专查假设漂移。
2. **复核变成橡皮章**：reviewer 与 worker 同模型同上下文会共谋。缓解：独立会话、只给证据、抽查结果反过来统计复核误判率。
3. **阶段越多越慢**：每个任务多两轮 agent 调用。缓解：简单任务跳过确认；复杂任务用「返工率下降」证明值得。
4. **拆分过度**：拆太碎导致复核成本爆炸。缓解：明确判据是「可独立验收」，且两轮后强制合并。
5. **模板僵化**：字段定死之后，新类型的任务套不进模板，写模板的人开始对着模板凑。缓解：模板只用 `--type` 选择、不强制；类型判断错时允许换；模板内容随档案里的观察演进，演进需要用户确认。

## 13. 留给实现的决定

- 澄清会话的提示词与轮数上限（建议 6 轮内出稿）。
- 复核 verdict 解析失败时的处理（建议按 `unclear` 处理，不按 `fail`）。
- 审计记录的字段集合与 `metrics` 的具体口径。
- 并行默认值（建议 2）。
