**九个判断的评审**（11-25 晚，所有者委托接手会话）

逐条对着设计 §4–§9、§16 和所有者的十条决定看过，没有要推翻的。每条一句：

1. 每轮从链首开始：窗口和轮次间隔一样长，不重置的话后几轮只剩链尾可试。
2. 证据只算本任务首次被拒之后被接受的回合：更早的接受会盖住之后才开始的整体故障。以「首次被拒」而不是「最近一次被拒」为界，是因为别的任务那一刻可能正好空闲，用后者会把任务自身的问题误报成整体故障。
3. 整体故障退出码 3 压过其他：退出码说明运行为什么停下；守卫的行和控制器错误照印在报告旁边。
4. 守卫拒绝的任务从记录里读：`status --stuck` 只读文件、立刻回答；它写明那是当时的结论，现在的结论看 `taskctl models`。
5. 提示词新增的那一行用中文：和其余固定文案一致；措辞仍然由所有者签。
6. 全冷却的一遍不算一轮：否则一个从没被问过的任务会凭别的任务的拒绝耗尽轮次。
7. §11 承接学习闭环推迟的那一项：学习闭环设计 §10 已经写明。
8. 手动 `retry` 保留最早的可领取时间、重新数轮次；复核阶段单独数；`run --batch` 不等窗口；被窗口挡住的 `retry --review-only` 明说并退出 1。
9. 停止不打断守卫读目录和检索记忆（各有 30 秒、20 秒的上界）；被停止的运行不判整体故障，因为那时的证据是停出来的；几个退出码取最严重的。

留意三点，都不构成问题：

- `run --batch` 被推迟停下时退出 0，而被窗口挡住的 `retry --review-only` 退出 1；脚本光看退出码分不出前者有任务没跑。
- 按 Ctrl-C 的运行如果同时有守卫拒绝或控制器错误，退出 1 而不是 130。
- 第 2 条有一个很窄的边角：别的任务的一个回合恰好在本任务首次被拒之后才结束，而它的模型调用其实发生在故障之前，这会把本任务判成自身问题；后果是那一个任务要手动 `retry` 一次。

### 需要你决定的事（没有擅自改）

1. **共享冷却策略**——唯一不是缺陷的 Blocker。任何一类供应商拒绝（含瞬时 5xx、鉴权、no-route）都让任务在一个失败回合后 `blocked`，并把看板锁 15 分钟；窗口内的手动 `retry` 会被立刻重新 park。设计 §14.1 的动机是配额耗尽。可选方向：只让 `quota` 类进表（改动最小）/ 给 `provider` 类一个短窗口 / N 次才进表 / 让 watch 到点自动重探。
2. **升级不告知 worker**——设计 §8.1 承诺「下一回合收到具体原因」，实际下一回合的提示词逐字节相同；渲染验收失败也不写返工笔记。要改提示词，需配一次有界 Live。
3. **§16 的车道分类推翻了 ADR-0008/0009**（「工具不自行降级」「没有分类器决定车道」），没有 supersession。相关：模型给的 `quick` 车道记进 `classification.json` 但按 `simple` 跑；意图里说「简单任务」只是模型未给分类时的缺省；没有强制签字的开关；watch 运行时模型判为 `simple` 的任务在有人读 spec 之前就被领取。写 ADR-0010，或把分类改成仅建议。

## 4. 这个仓库里验证有效的做法（请延续）

- 先写失败测试 → 实现 → 变异检查：一次只反转一个守卫，**先跑无变异对照组**，对照组不干净则整轮作废。
- **变异存活是测试设计信号，不是通过。** 这一轮两次存活，都是新回归自己分不清要测的路径；修的是测试，不是阈值。
- **回归要能确定性地打到目标路径。** 任务锁有两个心跳点——后台 tick，和 `controlled` 在每个受控操作前的刷新——它们争同一把任务互斥量。要指定谁先被拒，就在**互斥量之外**拖住主流程（适配器的 `resolveModel` 钩子）；用持有互斥量的慢操作（如 `store.list()`）只会把后台心跳挡在后面。
- **文件替换一律走 `renameWithRetry`**（`src/replace.ts`）。`tests/replace.test.ts` 有源码级守卫，出现裸的 `await rename(` 就失败（三处「移动到新名字」除外）。Windows 上的 EPERM 是真的：这台机器上 45 次里 3 次。
- **心跳写失败不等于丢锁。** 只有 `heartbeat` 返回 false、或受保护写入前的所有权检查失败，才结束尝试或 watcher。改这段逻辑时保住三条回归：后台心跳写失败、操作前刷新写失败、锁易主仍要结束。
- 模型选择的回归至少用三个模型——两模型链上索引错误碰巧不暴露。
- **测试桩必须镜像真实服务的形态。** `fake-opencode.mjs` 曾合成一个带 `model` 的 `session.get`，真实服务不这么回。改适配层时用控制面调用（`opencode api …`，不耗额度）核实真实形态。
- **入口要走真实 CLI。** `--resume` 的所有旧测试都把选项注入到解析器以下。
- 门槛用 `npm run typecheck`（11-25 起覆盖 `tests/`、`scripts/`、`vitest.config.ts`）；`npx tsc --noEmit` 只覆盖 `src/`。纳入时的 46 个错误说明：**测试替身必须满足接口**。`FakeStore` 缺 `incReviewRounds` 很久没人发现，因为从没有东西检查它。
- **假时钟测试对「计时器何时排上」有隐含假设**（11-25）。`tests/board-rename.test.ts` 一次性把时钟拨过整个预算，前提是所有等待在调用后的微任务里就排好；生产代码在两次等待之间加了一次真实 I/O（`lstat`），它就挂到超时。让每一段等待各自先获得一次真实事件循环（用启用假时钟之前捕获的 `setTimeout` 让出），断言不变。
- **变异体的「恒假条件」必须是常量**（11-25）。`Date.now() !== Date.now()` 是两次调用，时钟走一格就为真，曾让一个「永不放弃」的变异看起来像存活。用 `if (false)`，并确认每个变异是被「为它写的那条」杀死的。
- 匹配文本的缩进要从文件里数（11-25）。代码浏览工具的输出带行号前缀，我把 6 个空格看成 8 个，变异脚本因此匹配落空——脚本按设计中止，无损。
- **机械性的批量修改可以派给子代理，但要独立验证**（11-25）。给它写明约束（只改测试、不动断言、不用类型压制、需要改 `src/` 就停下报告）；自己重跑检查；统计每个文件删掉的断言行数（必须是 0）；比对改动前后的测试清单（只应多出预期的条目）。
- `tests/board-stress.test.ts`（50 轮 × 8 个写者，约 7 秒）是有意保留的（11-25）：它抓的是一个曾 10 次里出现 2 次的间歇故障，减少轮数等于把网放松。确定性的回归在 `tests/replace.test.ts` 和 `tests/board-rename.test.ts`。
- `maxWorkers: 4` 的依据是本机 24 个逻辑处理器下各 5 次运行零失败（11-25）。在更小或更忙的机器上，如果 `watch.test.ts` 之类的时序测试开始抖，先把 `vitest.config.ts` 里的值调回去。

- **PowerShell 变量名不区分大小写**：`$a` 和 `$A` 是同一个变量（本轮写聚合脚本时被它坑过）。数组字面量里的条目用逗号分隔，分组字典用按下标取值的数组。

- 用 `write` 新建的文件是 LF，工作区其余多为 CRLF；git 会提示 "LF will be replaced by CRLF"，无功能影响。

- **信号测试用手动的 `SignalSource`，从不给测试进程发真信号**（11-25 stop --now）。`createStopNow` 收注入的 `signals`，测试按需要触发 SIGINT/SIGTERM；真实信号只属于 Live 检查。
- **Windows 上的取消先列一次进程表，所以一次真取消要花约一秒**（11-25 stop --now）。`cancel()` 先用 `Get-CimInstance Win32_Process` 记下后代、再 `taskkill`，然后等它们消失、等管道关闭；把测试上界压到这以下的，测的是一个假取消。
- **`npx` 原样转发普通退出；控制台里的 Ctrl-C 则看中间那层包装**（11-25 stop --now；11-27 实测）。`run` / `watch` 的 130 / 143 是入口进程自己的码；普通退出（包括 `stop --now`，以及让进程自己收尾的 SIGTERM）经 `npx` 仍是这个码。控制台里按 Ctrl-C 时按键也到达 shell 与入口进程之间的包装进程：tsx 的 CLI（4.23.15）自己处理 SIGINT/SIGTERM，转给入口、等入口结束、再用入口的码退出——经 tsx 的 CLI 启动、输出直接进控制台时，pwsh 7.6.10 上（真 taskctl）停止完成、shell 一直等到入口进程结束才交回提示符（按键后约 2.5 秒）、退出码 130，Windows PowerShell 5.1 和 cmd 上（替身入口，cmd 那一次输出写到文件）退出码同为 130、提示符回来的时间没有计；经 `taskctl` 的 `.cmd` shim 启动、输出直接进控制台时，pwsh 7.6.10 和 Windows PowerShell 5.1 上（替身入口）同样完成并退出 130，cmd 下没有量；`npx` 自己的包装进程则随按键结束，pwsh 7.6.10 上提示符约 0.4 秒就回来、`$LASTEXITCODE` 是 1（npx 的码，不是 taskctl 的），停止本身照常完成；经 `npx` 启动这一种只在 pwsh 7.6.10 上量过。**最要留意输出：把控制器的输出接进 PowerShell 的管道或重定向（`| Tee-Object`、`> log`、`*> file`），PowerShell 会在按键被处理之后立刻杀掉原生命令**——停止请求没写、`attempt.json` 停在 `active`、任务停在 `running`、`watch.lock` 和回合的 worker 都留下（假入口被杀得一模一样，是 shell 的行为，不是 taskctl 的）；所以别把命令接进管道或重定向：`run` 有 `--log <file>`，`watch` 和 `retry --review-only` 没有这个选项（`watch --log` 被当作未知选项拒绝、退出 2），它们只把每个任务的事件行写进 `tasks/<id>/logs/run-<时间>.log`，控制器自己的行（例如 `[watch] stopped by the operator: a; run again to continue`）只打到控制台、不在任何文件里。这些是自有控制台里经控制台 API 发送的真实按键事件、不是可见窗口里的真人按键；对真实进程发送 SIGTERM、cmd 下经 `.cmd` shim 的启动（交互式 cmd 停止后是否会问 `Terminate batch job (Y/N)?` 也在其中）、Git Bash 等其它 shell 尚未实测。仓库没有文档化的无包装入口（v0.1 从源码用 `npx tsx src/main.ts` 运行），所以这只说明各启动方式下的实际样子，不是推荐哪一种。
- **被停下的控制器什么都不判**（11-25 stop --now）。被 stop 排空的尝试不是证据：`runScheduler` / `scheduleOnce` / `runBatch` 在 stop 待决时跳过整体故障判定，任务带着已花的轮次留在 `open`；`a run the operator stopped declares no outage`、`watch declares no outage under a stop`、`a stop ends a wait for a model window at once, and nothing is offered after it` 三条测试钉住它。
